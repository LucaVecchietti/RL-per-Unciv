# File 23.1 — Reward rework: stats accumulate + cities_alive + risorse tipizzate

## Obiettivo

Rivedere lo shaping del reward per (a) **differenziare per tipo di risorsa connessa** (Bonus /
Strategic / Luxury), (b) introdurre **reward continuo sulle statistiche accumulate** (science,
gold, culture, happiness, faith), (c) invertire il **trend calante di `cities_founded`**
osservato in Run #22. Tutto via config, senza toccare obs shape e action space.

## ⚠️ Prerequisito

Nessun prerequisito di engine: la rework è **solo Python**. Il run #22 (500k step) ha già
validato la stabilità del training post-fix Sessione 40/41. **Non richiede rebuild JAR**, non
cambia il contratto headless, non cambia il contratto obs/azioni.

> ⚠️ Questo file è numerato **23.1** intenzionalmente: va implementato **prima** del File 23,
> perché ne migliora i prerequisiti di shaping (in particolare la dinamica espansione + risorse
> su cui poggia l'attivismo del Worker della Fase 23).

## Stato attuale

Pesi in `src/utils/reward.py` (`REWARD_WEIGHTS`):

- `exploration: 0.3`, `found_city: 5.0`, `resource_placement: 2.0`, `resource_connected: 3.0`
- più i legacy: `population_growth`, `tech_researched`, `gold_accumulation`, ecc.

Anomalie osservate in Run #22 (500k step, eval finale 176):
- `cities_founded_mean` cala da 2 → 0-1 nel corso del training; `action_FoundCity` scende
  0.05 → 0.002.
- `connected_resources_mean` resta in [0, 1] (sporadico, segnale poco utile).
- `techs_mean ≈ 18` costante (nessuno shaping sul *progresso* tech, solo sul completamento).
- `units_stuck_mean` 50-100, variabile (no penalty diretta).
- `eval/mean_reward`: 166 → 176 (positivo ma plateau a fine).

Il segnale di reward è troppo discreto (eventi rari) e mal differenziato: lo shaping non
trasferisce informazione fra eventi → l'agente regredisce sull'espansione.

## Design

### 1. Tipizzazione `resource_connected`

Rimpiazzare il peso unico `resource_connected: 3.0` con **3 pesi tipizzati**:

| Tipo risorsa | Peso | Esempi |
|---|---|---|
| `resource_connected_bonus` | `3.0` | Banana, Wheat, Stone, Cattle |
| `resource_connected_strategic` | `4.0` | Iron, Horses, Coal, Oil |
| `resource_connected_luxury` | `5.0` | Gems, Silk, Spices, Gold (luxury) |

Infrastruttura già pronta: `ruleset_reader.load_resource_types(jar_path)` ritorna mapping
`nome → tipo`. In `state_parser.py` il filtro `resource_tiles` oggi include solo
Strategic/Luxury → **estendere** a includere "Bonus".

### 2. Stats accumulate (5 pesi uniformi)

Peso uniforme **0.25** su 5 statistiche: `science_accumulated`, `gold_accumulated`,
`culture_accumulated`, `happiness_accumulated`, `faith_accumulated`.

- **Delta turn-per-turn**, NON cumulativo (PPO + Gymnasium: il cumulativo fa esplodere la
  varianza del critic).
- **Clip a 0 sui delta negativi**: `max(0, curr.X - prev.X) * weight`. Non penalizziamo cali
  transitori naturali (es. acquisto di un edificio che svuota il tesoro).
- Sorgenti:
  - `science/gold/culture`: delta sulle stat `per_turn` o accumulate (decidere in implementazione
    in base a cosa è già in `GameState`).
  - `happiness`: delta sul livello accumulato.
  - `faith`: campo `GameState.faith_per_turn` da aggiungere (default `0.0` — "armato ma inerte"
    finché il parsing del save non lo popola).

### 3. Cities_alive_bonus + riduzione `found_city`

- `found_city`: **da `5.0` a `3.0`** (decisione confermata).
- Nuovo `cities_alive_bonus: 0.05` per turno, per ogni città **oltre la prima**:
  `reward += max(0, len(curr.cities) - 1) * 0.05`.

Razionale: convertire un segnale one-shot (`found_city`) in un **continuum** denso. La somma
preserva il segnale totale di espansione ma con gradiente smussato → policy meno fragile sulla
decisione di fondare.

### 4. Altri shaping

| Componente | Peso | Note |
|---|---|---|
| `tech_progress` | `0.5` | Delta normalizzato `(progress/cost)` clippato `[0, 1]`. Sblocca `techs_mean = 18`. |
| `units_stuck_penalty` | `0.02` | Per unità stuck. Target `stuck_mean < 30`. |
| `happiness_bonus` | `0.05` | Cap `0.05/turno` se `happiness > 5`. Riduce risk-aversion. |
| `building_diversity` | `0.5` | Una tantum per ogni building nuovo nel set totale civ. Anti-Walls-spam. |

### 5. Feature flag via config

Tutti i nuovi pesi vivono in `config/default_config.yaml` sotto `reward:`. **Disattivazione =
peso 0.0** (no PR multiple per ablation: si imposta a zero e si rilancia).

### 6. Pesi finali — tabella

```yaml

  found_city: 3.0                   # da 5.0
  resource_placement: 2.0           # invariato
  resource_connected_bonus: 3.0     # nuovo (ex resource_connected)
```

## Implementazione

### `src/utils/reward.py`
- Aggiornare `REWARD_WEIGHTS` con i nuovi pesi (vedi tabella).
- Estendere `compute_reward(prev, curr, action, weights, skip_action_idx)`:
  - **3 blocchi distinti** per `resource_connected_*`: leggere
    `curr.connected_bonus / connected_strategic / connected_luxury` da `GameState`, comparare con
    `prev.*` e applicare il peso tipizzato.
  - **5 blocchi `*_accumulated`**: `max(0, curr.X - prev.X) * weight`.
  - **`cities_alive_bonus`**: `max(0, len(curr.cities) - 1) * weight` ogni turno.
  - **`tech_progress`**: delta su `(progress / cost)` clippato `[0, 1]` × peso.
  - **`units_stuck_penalty`**: `-weight * n_stuck`.
  - **`happiness_bonus`**: `weight if curr.happiness > 5 else 0` (cap implicito = peso).
  - **`building_diversity`**: tenere set cumulato `seen_buildings`; per ogni building **nuovo**
    nel turno corrente → `+weight` una tantum.
- Mantenere **firma invariata**. Valutare in implementazione un breakdown dict opzionale per
  debug/callbacks (utile per il TB ma non vincolante in questa spec).

### `config/default_config.yaml`
- Sezione `reward:` allineata 1:1 alla tabella sopra. Default scelti per non rompere i run
  esistenti (`found_city` cambia da 5.0 a 3.0 — atteso).

### `src/parsers/state_parser.py`
- `GameState`:
  - aggiungere `connected_bonus: int = 0`
  - aggiungere `faith_per_turn: float = 0.0`
- `CityState`:
  - aggiungere `territory_bonus: int = 0`
- In `_extract_game_state`:
  - estendere il filtro `rtype` di `resource_tiles` a includere `"Bonus"` (oggi solo
    Strategic/Luxury).
  - contare `connected_bonus` parallelamente a `connected_strategic / connected_luxury`.
- **NON toccare** `to_observation_vector`: shape `(61,)` resta invariata. I nuovi campi sono
  consumati **solo** da `reward.py` (e dai callbacks per monitoring).

### `src/utils/ruleset_reader.py`
- **Nessuna modifica**: `load_resource_types` già ritorna `Bonus / Strategic / Luxury`.

### `src/utils/callbacks.py` (`UncivMetricsCallback`)
- Splittare `unciv/connected_resources_mean` in 3 metriche:
  `unciv/connected_bonus_mean`, `unciv/connected_strategic_mean`, `unciv/connected_luxury_mean`.
- Aggiungere `unciv/reward_breakdown_*` per le componenti principali
  (`tech_progress`, `stats_accumulated_total`, `cities_alive_total`) tramite info dict dell'env
  — utile per debugare quale shaping sta dominando.

### `src/envs/unciv_env.py`
- Verificare che `units_stuck` sia esposto nell'info dict (per la metrica e per la penalty).
  Se non lo è → aggiungere.

## Criteri di accettazione

- Suite test: **132 + ~15 nuovi → tutti verdi**.
- Training run di validazione **50k step**:
  - `ep_rew_mean ∈ [180, 250]` (no esplosione).
  - `connected_resources_mean ≥ 1.5` (era 0-1).
  - `techs_mean ≥ 20` (era 18).
  - `cities_founded_mean ≥ 1.5` (inverte il trend calante).
  - `action_FoundCity ≥ 0.005` (era 0.002).
  - `eval/mean_reward > 150` (non collassato).
- **Failure mode esplicito**: se `ep_rew_mean > 400` oppure `units_stuck_mean > 150` →
  rollback config (pesi nuovi al 50%).

## Rischi / open questions

| Rischio | Mitigazione |
|---|---|
| `science_accumulated 0.25 × delta` → degenerazione tech-only | Peso uniforme su 5 stats: science non domina da sola |
| `gold_accumulated 0.25 × delta` → spam Market | `cities_alive_bonus` bilancia il segnale espansione |
| `cities_alive_bonus 0.05/turno` → spam Settler early | Costo Settler da ruleset + `found_city` ridotto a 3.0 |
| `tech_progress 0.5 × delta` → ciclo su tech facili | `tech_researched 3.0` resta sul completamento, premiando le tech finite |
| `building_diversity 0.5` → spam Walls inutili | Una tantum per building nel set totale → impatto cap `≤ +4-5` per episodio |
| `faith_accumulated` armato ma inerte | Documentato come tale; si attiverà col parsing faith dal save |

> Open: il peso 0.25 uniforme può comunque sbilanciare verso science (che cresce di più
> nell'early game). Da rivedere a 50k step se una stat domina nettamente nel breakdown.
